## 一、应用锁改为「每次回前台都验」

### 1.1 现状与根因

`core/common/AppLockGuard.kt` 里有一个 60 秒宽限期：

```kotlin
fun onForeground() {
    if (!state.enabled) return
    val away = if (backgroundAt < 0) 0 else now() - backgroundAt
    backgroundAt = -1
    if (away >= BACKGROUND_GRACE_MS) {      // ← 60_000
        state = state.copy(locked = true, failedAttempts = 0)
    }
}
```

按 Home 键回桌面、再点图标回来，间隔通常 2～5 秒，`away < 60_000`，因此**不上锁**。这就是用户说的「返回桌面再进入就不需要指纹了」。

> 这个宽限期是 v1.9.0 为「跳去相册挑图不该重新按指纹」加的，现在被证明代价大于收益：用户在不知情的情况下失去了锁的意义。

### 1.2 定稿

**宽限期归零。除白名单外，任何一次「离开前台 → 回到前台」都立即上锁。**

| 项 | 定稿 |
|---|---|
| 宽限期常量 | `BACKGROUND_GRACE_MS` **删除**，不再按时间判断 |
| 判定 | `onForeground()` 只要 `state.enabled` 且 `backgroundAt >= 0` 就置 `locked = true` |
| 转屏/分屏/深色模式切换/字号切换 | **不上锁**。这是配置变更，人没离开 |
| 相机 / 相册 / 文件选择器 | **不上锁**（见 1.3 白名单） |
| 冷启动 | 行为不变，`configure()` 里首次开锁即 `locked = true` |
| 未开锁 | 仍为 no-op，不弹任何东西 |

### 1.3 白名单：本 App 主动拉起的「外部 Activity」

系统相机、系统相册、SAF 文件选择器都是**独立 Activity**，拉起时本 App 必然走 `onStop`。如果不豁免，用户拍完照回到 App 第一眼是锁屏，刚拍的照片还挂在被回收的页面状态里，拍照功能等于废掉。

做法：给 `AppLockGuard` 增加一对纯逻辑 API，不引入任何 Android 依赖，保持可单测：

```kotlin
/** 本 App 主动跳去外部 Activity（相机/相册/文件选择）时登记，回来后不因这次离开而锁屏。 */
fun beginTrustedLeave()

/** 外部 Activity 已返回（无论成功、取消、失败）。 */
fun endTrustedLeave()
```

三个方法的配合（**豁免只生效一次**，这一点必须写死，否则会漏锁）：

| 调用 | 行为 |
|---|---|
| `beginTrustedLeave()` | `count++`，记下 `trustedLeaveAt` |
| `onBackground()` | `count > 0` → 不记 `backgroundAt`（保持 -1）；否则开始计时 |
| `onForeground()` | `count > 0` 且未过期 → **`count = 0` + 不上锁**；否则按第一节正常上锁 |
| `endTrustedLeave()` | `count = max(0, count - 1)`，仅用于提前归还名额 |

> 关键在 `onForeground()` 里把 `count` **清零**而不是减一：一次返回只豁免一次。否则用户从相机回 App、再按 Home、再回来——第二次仍会被豁免，锁就形同虚设。

| 约束 | 定稿 |
|---|---|
| 嵌套计数 | 用 `Int` 而非布尔，防止「A 还没回调、又从 A 里拉起 B」时被提前清掉 |
| 兜底过期 | `beginTrustedLeave()` 记时间戳；若 `now() - trustedLeaveAt > 10 分钟`，`onForeground()` 视为过期，**强制清零并上锁**。防「外部 Activity 被系统杀掉、回调永远不来」导致锁彻底失效 |
| 登记点 | `rememberPhotoCapture` 的 `takePhoto` / `pickPhoto` 启动前；`ActivityResult` 回调第一行 `endTrustedLeave()` |
| 登记点 | 备份导入/导出、CSV 导出的 `OpenDocument` / `CreateDocument` 启动前 |
| **不登记** | 系统分享面板、通知栏下拉、多任务切换、按 Home —— 这些必须上锁 |

### 1.4 配置变更如何排除

`MainActivity` 里：

```kotlin
override fun onStop() {
    // 转屏 / 分屏 / 深色模式 / 字号变化都会走 onStop→onStart，人并没有离开
    if (!isChangingConfigurations) lockGuard.onBackground()
    super.onStop()
}
```

`isChangingConfigurations` 在配置变更期间为 `true`，这是 Android 提供的官方判据，比自己比较宽高可靠。

### 1.5 一个必须一起处理的坑

`configure()` 里 `locked` 只取决于 `enabled`。如果用户开了应用锁但**既没设 PIN 也没录生物特征**，一旦上锁就是死锁，只能清数据。

现状靠 v1.9.0 的「开锁时必须同时设 PIN」兜住，本轮把它升级为硬约束：

> `configure(enabled = true, hasPin = false)` 时**不允许上锁**，并记一条日志。理论上到不了这一步，但不该让一条错误路径把用户锁在门外。

### 1.6 验收

| 操作 | 期望 |
|---|---|
| 开锁状态下按 Home，1 秒后点图标回来 | **立即弹指纹/PIN** |
| 开锁状态下按返回键退出 App，再冷启动 | 弹指纹/PIN |
| 记账页点相机 → 拍完返回 | **不弹锁**，照片已挂上 |
| 记账页点相机 → 点取消返回 | 不弹锁 |
| 记账页点相册 → 选图返回 | 不弹锁 |
| 记账页转屏 | 不弹锁 |
| 明文通知栏下拉看一眼再回来 | 弹锁 |
| 相机 Activity 被系统杀掉（可模拟：开发者选项「不保留活动」） | 10 分钟后强制恢复上锁，不会永久不锁 |

## 二、记账页记忆分类与付款账户

### 2.1 现状

| 项 | 现状 |
|---|---|
| 分类 | `EditorViewModel.init` 里没有任何「上次分类」读取，每次新建都是干净 state，分类必选 |
| 付款账户 | 设置里**已有** `defaultAccountId`（设置页「默认账户」），但 `EditorViewModel` 从未读过它 |
| 账户预选 | 只有一条弱兜底：`fundAccounts.size == 1` 时自动选唯一账户 |
| 类型 | `lastTxnType` 已持久化，切换类型会记住，这一条不用改 |

结论：分类记忆**完全没有**，账户记忆**有设置项但没接线**。

### 2.2 定稿：两级记忆 + 兜底链

新增两个设置项（`SettingsDataStore` / `SettingsSnapshot` / `SettingsRepository` 三处同步）：

| Key | 类型 | 含义 |
|---|---|---|
| `last_expense_category` | `String?` | 上次保存成功时用的支出分类 id |
| `last_income_category` | `String?` | 上次保存成功时用的收入分类 id |

付款账户复用 `default_account` 作为**兜底**，另加 `last_pay_account` 记住「上一次实际用的账户」：

| Key | 类型 | 含义 |
|---|---|---|
| `last_pay_account` | `String?` | 上次保存成功时用的付款账户 id |

取值优先级：

```
付款账户：last_pay_account（仍存在且未归档）
        → default_account（设置里的「默认账户」）
        → 唯一的资金账户
        → 不预选

分类：   last_{type}_category（该类型下，仍存在且未隐藏）
        → 该类型下 usageCount 最高的分类
        → 不预选
```

| 时机 | 是否写入记忆 |
|---|---|
| 新建并保存成功 | **写入**（type / category / account 三项一起写） |
| 编辑已有账目并保存 | **不写入**。老账目的分类不代表用户当前习惯，写进去等于用历史污染记忆 |
| 套用模板 | **不写入**。模板自带分类，不代表用户习惯 |
| 组合支付保存 | 写入**第一个**账户（分摊里金额最大的那个），因为组合里的「主账户」才是下次真正会用的 |

### 2.3 失效数据的处理

`last_pay_account` 指向的账户被删除或归档后，不能出现「记账页显示一个不存在的账户」：

- 读取时校验：账户列表里找不到该 id，或 `archived = true`，视为无效，跳到下一级兜底；
- 分类同理：`hidden = true` 或已删除，视为无效；
- 无效值**不回写**（不清空设置），用户换个账户用一次就会自然覆盖。

### 2.4 一个边界：切换类型时分类要不要跟着换

用户在支出里选了「晚餐」，切到收入时，「晚餐」是一个支出分类，绝不能留在 `categoryId` 里——否则会存出一笔「收入 / 晚餐」的错账。

定稿：**`setType()` 切换时，按新类型重新初始化 `categoryId`，而不是无条件置 null。**

| 新类型 | `categoryId` 取值 |
|---|---|
| 支出 | 支出侧记忆分类 → 支出最高频分类 → null |
| 收入 | 收入侧记忆分类 → 收入最高频分类 → null |
| 转账 / 借贷 | 恒为 null（不选分类） |

这样一来：

- 切到收入不会被支出分类污染；
- **切回支出时能恢复「晚餐」**，而不是清空——顺手解决了「误触 tab 后已选分类丢失」的老问题；
- 同一类型内重复点同一个 tab 不改动任何东西（`if (type == _state.value.type) return` 保持）。

> 注意与 `PRDv1.9.0` 3.5 的关系：借贷类型仍然不选分类，`setType(DEBT)` 时 `categoryId` 必须为 null。

### 2.5 验收

| 操作 | 期望 |
|---|---|
| 新建支出，选「晚餐」，存一笔 | — |
| 再点＋新建支出 | 分类已预选「晚餐」，账户预选上次账户 |
| 新建收入 | 分类是收入下上次用的（没记过则用最高频），**不能**是「晚餐」 |
| 收入选「工资」存一笔，再切到支出 | 分类回到「晚餐」，不是空的 |
| 编辑一笔 3 个月前的账 | 打开后分类/账户是那笔账的，不是记忆值 |
| 设置里把默认账户改成 B，从未用 B 记过账 | 新建时预选 B（`last_pay_account` 为空时走默认账户） |
| 把上次用的账户删掉 | 新建时自动退到默认账户，不报错、不显示空账户 |

## 三、相机闪退修复

### 3.1 根因（三条，都会崩或卡）

**根因 A：声明了 CAMERA 却没申请**

`AndroidManifest.xml` 第 21 行：

```xml
<uses-permission android:name="android.permission.CAMERA" />
```

这是 v1.9.1 加进去的。而全仓库**没有任何运行时权限申请**（`grep requestPermission` 零命中）。

Android 的规则是：只要清单里声明了 `CAMERA`，`MediaStore.ACTION_IMAGE_CAPTURE` 就要求该权限**已授予**，否则在 `startActivity` 的瞬间抛：

```
java.lang.SecurityException: Permission Denial: starting Intent { act=android.media.action.IMAGE_CAPTURE }
requires android.permission.CAMERA
```

表现就是点「拍照」立刻闪退。相册走 `PickVisualMedia`，不需要权限，**这条路径本身是好的**。

**根因 B：大图解码在主线程**

`EditorPhoto.kt` 的 `compressTo()` 在 `ActivityResult` 回调里同步执行：读 bounds → 按采样率解码 → EXIF 旋转（可能再分配一张图）→ 缩放（再分配一张）→ 压缩写盘。

一张 4000×3000 的照片，这段在低端机上 1～3 秒。主线程卡住超过 5 秒就是 ANR，用户感知同样是「点了就卡死/闪退」。即使不 ANR，这期间任何触摸都被吞掉。

**根因 C：采样率判据写错，大图按原尺寸解码**

`EditorPhoto.sampleSizeOf()` 原本是：

```kotlin
while (width / (sample * 2) >= MAX_PHOTO_EDGE && height / (sample * 2) >= MAX_PHOTO_EDGE) {
    sample *= 2
}
```

`&&` 要求**长边和短边都**达到 3200 才降采样。一张 4000×3000 的相机原图，短边 3000/2 = 1500 < 1600，条件不成立，`sample` 停在 1——于是 `BitmapFactory` 按 4000×3000 全尺寸解码，单张位图约 **48MB**。加上解码缓冲与旋转时的第二张副本，峰值逼近 100MB，低端机直接 `OutOfMemoryError`。

这是「闪退」的第三个独立原因，而且它和权限无关：**即使权限全给了，只要照片够大照样崩**。正确判据是只看长边。

### 3.1.1 验证方式

三条根因靠一张测试表区分：

| 现象 | 指向 |
|---|---|
| 点「拍照」立刻崩，什么都没发生 | 根因 A（权限） |
| 拍完、回到 App 的一瞬间卡住然后崩 | 根因 B（主线程） |
| 拍完回 App 后崩，且是大分辨率照片 | 根因 C（采样率） |
| 从相册选图也崩 | 只有 B / C，与权限无关 |

### 3.2 定稿

| # | 修法 |
|---|---|
| A1 | 保留 `CAMERA` 声明（拍照确实需要），补上运行时申请 |
| A2 | 点「拍照」时先 `ContextCompat.checkSelfPermission`；已授予直接启动，未授予先申请 |
| A3 | 授权回调里：授予 → 立刻启动相机；拒绝 → Snackbar 提示「未授予相机权限，已为你打开相册」+ **自动拉起相册** |
| A4 | 拒绝且「不再询问」（`shouldShowRequestPermissionRationale == false` 且未授予）→ 对话框说明原因，给「去设置」按钮跳 `ACTION_APPLICATION_DETAILS_SETTINGS` |
| A5 | 设备没有相机 App（`resolveActivity == null`，部分平板/模拟器）→ 按钮仍可点，点了直接进相册并提示 |
| B1 | `compressTo()` 整体挪到 `Dispatchers.IO`。`rememberPhotoCapture` 里取 `rememberCoroutineScope()`，回调中 `scope.launch(Dispatchers.IO)` 跑压缩，成功回到主线程 `onCaptured(path)`。**不要在 composable 里直接调 `viewModelScope`**——照片不属于业务状态机，塞进 ViewModel 反而多一层耦合 |
| B2 | 压缩期间在相机按钮上显示一个小 `CircularProgressIndicator`，禁止重复点击 |
| B3 | 压缩失败（返回 null）→ 提示「照片处理失败」，不写入 `photoPath`，不崩 |
| C1 | `sampleSizeOf` 判据改为只看长边：`while (maxOf(w, h) / (s * 2) >= MAX_PHOTO_EDGE)` |
| C2 | 补断言：4000×3000 → 采样 2（解码后 2000×1500，约 12MB），8000×6000 → 采样 4 |

**不改的部分**：`FileProvider` 配置（`${applicationId}.fileprovider` 与 manifest 已一致）、`file_paths.xml` 已有 `cache-path`、`compressTo` 的采样/旋转/缩放算法。

### 3.3 权限申请的归属

不要写在 `EditorPhoto.kt` 里——它是个工具文件，塞权限逻辑会让它变成「什么都管」。

新建 `feature/editor/PhotoPermission.kt`：

```kotlin
/** 相机权限的申请与降级（v1.9.3 第 3 条）。 */
@Composable
internal fun rememberCameraGate(
    onGranted: () -> Unit,
    onDenied: () -> Unit,      // 降级到相册
    onBlocked: () -> Unit,     // 需要去设置
): CameraGate
```

`EditorScreen` 里 `showPhotoMenu` 选「拍照」时调用 `gate.request()`。

### 3.4 验收

| 操作 | 期望 |
|---|---|
| 首次安装，点相机 → 拍照 | 弹系统权限框；允许后进相机，拍完回填缩略图 |
| 拒绝权限 | 不崩；提示后自动进相册 |
| 拒绝并勾选「不再询问」 | 弹说明对话框，「去设置」能跳到本 App 权限页 |
| 已授权，连拍 5 张 | 每张都有缩略图，无卡顿、无 ANR |
| 拍一张 4000×3000 的原图 | 存盘后长边 1600，文件约 200～500KB |
| 相机 App 不存在（模拟器） | 直接进相册，有提示 |
| 选完照片又点 × 移除 | 缩略图消失，保存后 `photoPath` 为空 |

### 5.3 引线标签

| 项 | 当前 | 定稿 |
|---|---|---|
| 文本 | 第一行账户名，第二行占比 | **一行**：`账户名 数值`，中间一个空格 |
| 文本内容 | 恒为百分比 | 跟随模式：金额模式 `1,200.21`（千分位，无 `¥`），占比模式 `62.04%` |
| 对齐 | 右侧左对齐、左侧右对齐 | **两侧都左对齐**（参考图左侧的「储蓄卡」「投资账户」左边缘在同一竖直线上） |
| 字号 | 12sp | 12sp 不变 |
| 换行 | 不换行，超出截断 | 允许两行：名字一行、数值一行（图里「待报销 现金 18.00」就是长名字换行） |
| 颜色 | `onSurfaceVariant` | 名字 `onSurfaceVariant`，数值 `onSurface`（数值略重，便于扫读） |
| 引线 | 环外缘 → 肘部 → 水平线段 + 起点 2dp 圆点 | 不变，这套几何已经过六组极端数据的数值验证，不动 |

左侧改左对齐后，引线的水平段长度会随文字长度变化，需要把 `calloutSpace` 从 78dp 适度放宽到 **88dp**，并把最小行距从 27dp 提到 28dp，避免两行文本撞在一起。

两个实现要点：

- **引线起点用 `Paint.measureText` 取文字实际宽度**，不要用列宽。左对齐后短标签右侧会留白，若从列右缘起画，短标签的引线会凭空漂在空白里。
- **左侧列的锚点**：文字左边缘固定在 `paddingStart`，引线从「文字末端 + 4dp」向右折到环上锚点；右侧列相反。两侧共用同一套 `placeSide()` 防重叠逻辑，只把「文字宽度」的取值方式换掉。

**改完必须重跑几何模拟**（8 等分 / 1 大 7 小 / 2 段 / 单段 / 5 段不均 / 7 段极端），确认零重叠零越界再落代码。

**圆形图标怎么画**（这里有个坑，必须先定死）：

`Category.icon` 与 `Category.color` 两个字段虽然从 v1.0 就在表里，但**种子数据里填的是无意义的值**：

```kotlin
icon = "wallet"          // 大类：一个英文单词
icon = majorId           // 小类：父分类的 id
icon = ""                // 叶子：空
color = ""               // 全部为空
```

也就是说，仓库里**没有一套能直接渲染的图标体系**，`icon` 里既不是 emoji 也不是资源名。

定稿方案：**关键词映射 + 首字兜底**，不改数据、不加字段。

| 步骤 | 规则 |
|---|---|
| 1. 底色 | `color` 是合法的 `#RRGGBB` 就用它；否则 `palette[abs(name.hashCode()) % palette.size]`，palette 是一组 12 色柔和色 |
| 2. 图标 | 分类名**包含**关键词表里的词 → 用对应 Material 图标（白色，16dp） |
| 3. 兜底 | 都不命中 → 画分类名**第一个字**（白色，14sp `Bold`，居中） |

### 6.9 键盘

参考图是 4 列 × 4 行，右侧一列是功能键：

| 行 | 列 1 | 列 2 | 列 3 | 列 4 |
|---|---|---|---|---|
| 1 | `1` | `2` | `3` | `⌫`（紫底） |
| 2 | `4` | `5` | `6` | `再记`（浅蓝底） |
| 3 | `7` | `8` | `9` | `保存`（浅蓝底，**跨 3~4 行**） |
| 4 | `⌨`（切换计算器） | `0` | `.` | ↑ 被「保存」占据 |

| 项 | 定稿 |
|---|---|
| 容器 | 键盘区底色 `surfaceContainer`（比页面略深），顶部 1dp 分隔线，底部吃 `navigationBars` inset |
| 数字键 | 白色胶囊，圆角 12dp，高 48dp，字号 22sp `Medium`，`onSurface` |
| 键间距 | 8dp |
| `⌫` | `tertiaryContainer` 底（偏紫），图标 `Icons.AutoMirrored.Filled.Backspace`；**长按清空全部**（v1.9.1 已有，保留） |
| `再记` | `primaryContainer` 底，`onPrimaryContainer` 字，字号 14sp |
| `保存` | `primaryContainer` 底，**跨第 3、4 行**，高度 = `48 × 2 + 8` = 104dp，字号 15sp `SemiBold` |
| `⌨` | 切换「纯数字」⇄「四则运算」。图标在数字模式显示 `Icons.Outlined.Calculate`，计算器模式显示 `Icons.Outlined.Dialpad` |
| 计算器模式 | 在原 4 行**上方多插一行** `+ − × ÷`，下面 4 行的位置与尺寸完全不变（保存仍跨第 3~4 行）。**不另设 `=` 键**——按下的「保存」本身就承担求值，算完就是要入账，多一个等号是多余的一步 |
| 禁用态 | 金额为 0 或未选分类时，「保存」置灰（`alpha 0.4`），点击无反应但给 Snackbar 提示缺什么 |

**键区必须是手写 `Row × Column`，不能用 `LazyVerticalGrid`**：`LazyVerticalGrid` 无法让「保存」跨两行，这正是这块最容易写歪的地方。结构：

```
Row {
  Column(weight = 3f) { 4 行数字，每行 3 个键 }   // 1 2 3 / 4 5 6 / 7 8 9 / ⌨ 0 .
  Column(weight = 1f) {                          // 右侧功能列
      ⌫（48dp）
      再记（48dp）
      保存（104dp = 48 * 2 + 8）
  }
}
```

**「再记」的语义**（新功能）：

| 项 | 定稿 |
|---|---|
| 行为 | 先走完整保存流程；成功后**不关页**，清空 `amount` / `note` / `photoPath` / 标签 / 商家 / 报销 / 退款 / 分期 / 不计入 |
| 保留 | `type` / `categoryId` / `accountId` / `dateTime`（图里「再记」就是连续记同类账） |
| 反馈 | 保存成功后顶部滑入一条 `Snackbar`「已记一笔 ¥50.00」，页面不跳转 |
| 编辑模式 | **不显示「再记」**，该格留空但**保留同尺寸占位**，「保存」仍跨第 3~4 行。不留占位会让「保存」变高、整个键盘高度跳动 |
| 记忆 | 「再记」与普通保存一样写入分类/账户记忆 |

### 7.2 为什么用弹层而不是跳页

跳页会**丢掉当前已填的金额、备注、照片**。用户点了爱心才发现模板里没有想要的，返回后一切归零，这是很糟的体验。弹层原地覆盖，关掉就回到原状。

模板页仍然保留在抽屉里，作为「管理」（增删改）的入口，两者分工清晰：**爱心 = 用模板，设置里的模板页 = 管模板**。

### 7.3 与现有 `loadTemplate` 的关系

`EditorViewModel.loadTemplate(id)` 已经存在（v1.9.1 通过 `Routes.editor(templateId = id)` 使用）。本轮只需要：

- 弹层选中后直接 `viewModel.loadTemplate(id)`，**不再走路由**；
- `Routes.editor(templateId = ...)` 这条路径**保留**（明细页的「套模板」入口还在用），不删。

## 十、执行顺序

**缺陷先行（1、3）→ 记忆（2）→ 报表（4、5）→ 记账页（6、7）**

理由：

1. **1 和 3 是缺陷**，先修，且互相独立，各改各的文件，可以并行验证；
2. **2 要动 `SettingsDataStore` / `SettingsSnapshot` / `SettingsRepository` 三处**，先把这层改完，第 6 条重写记账页时直接接线，不用二次返工；
3. **4 是 5 的前置**（先换页头再谈卡片样式），5 内部顺序是「卡片容器 → 圆心 → 引线 → 总额 → 分段控件 → 删图例」；
4. **6 和 7 共用页头**，一起做；6 内部顺序是「Tab → 分类金额行 → 快捷分类 → 付款账户 → 备注 → 状态胶囊 → 键盘」，从静态布局到交互逐层推进，每完成一区就能单独截图比对。

风险最高的两处：

- **第 5 条的引线标签左对齐**：改了 `calloutSpace` / 行距，几何算法必须重跑数值模拟再落代码，否则必然重叠。
- **第 6 条的键盘「保存」跨两行**：`Row` 里跨行要靠 `Column` 嵌套 + `weight`，`LazyVerticalGrid` 做不到跨行，必须手写 `Row × Column`。这里最容易写成两套高度不同步。

改完统一走：`compileDebugKotlin` → `ktlintCheck` → `detekt` → `testDebugUnitTest` → `assembleRelease` → aapt2 权限核对 → 真机走一遍第八节验收表。
