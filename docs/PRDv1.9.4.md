## 二、① 资产报表饼图引线

### 2.1 现状

`LabeledPieChart.drawCalloutLines()` 现在的画法：

```
起点 = 外缘 (center + 单位向量 × 外半径)
  ↓ 斜线
肘部 = (center.x ± (外半径 + 12dp), labelY)
  ↓ 水平线
文字 = labelY 处的标签基线
```

问题：起点在外缘，等于线从色块最外侧「飞出去」；12dp 的肘部外扩让折线在饼图外侧再兜一个弯，视觉上引线有两条折痕，且与色块的联系很弱。起点还画了一个 2dp 的圆点——圆点压在色块边缘上，看起来像是色块被咬了缺口。

### 2.2 目标几何

```
起点 = 环中线 (center + 单位向量 × (外半径 − 线宽/2))
  ↓ 沿扇区中角直出 4dp
拐点 = center + 单位向量 × (外半径 − 线宽/2 + 4dp)
  ↓ 折线
肘部 = (center.x ± (外半径 + 4dp), labelY)
  ↓ 水平线
文字边缘
```

**要点**：

- **起点在色块内部**：环中线是描边的中心线，起点就在环带正中；4dp 的直出段也仍有一部分落在环带里（环带宽 24dp，半宽 12dp）。
- **先直后折**：引线前 4dp 沿着扇区自己的方向，与「这块属于这个角度」的语义对得上；之后再折向水平。
- **去掉起点圆点**：起点埋进色块内部了，圆点会变成色块上的一个斑点。
- **肘部偏移 12dp → 4dp**：折线在饼图外只兜 4dp，接近「贴着饼边走」。
- **标签列 88dp → 96dp**：账户名可用宽度从约 70dp 增加到约 86dp，减少「投资账户 2,000.00」这类长标签折成两行的概率。

### 2.3 选中扇区的起点取法（**裁定：不跟随选中态**）

`drawRing()` 里选中扇区的描边宽度是 `线宽 × 1.25`，描边居中，所以它的真实环中线比未选中扇区靠里 1.5dp（`24 × 0.25 / 2 = 3dp` 的外扩，中线偏移为其一半）。

**决定：起点统一取 `外半径 − 线宽/2`，不随选中态变化。** 理由：

1. 代价可忽略：选中时起点落在自己色块内偏外 1.5dp 左右，色块本身占了 30dp 宽，肉眼看不出偏。
2. 收益是稳定性：起点跟着选中态变，点击切换时会看到所有引线的根部一起微微抖动，反而更显眼。

### 2.4 保留不变的部分

| 项 | 取值 |
|---|---|
| 字号 | 11sp |
| 省略与折行 | 优先单行 `名字 数值` → 超宽折两行 → 名字再超宽加省略号 |
| 选中态 | 选中段与未选中段的颜色透明度规则（未选中 0.35）不变 |
| 左侧对齐 | 两侧都左对齐（左列 x=0、右列贴画布右边） |
| 防重叠 | 按扇区中角的 cos 分两列，按各自实际高度递推最小间距，再夹回画布 |

### 2.5 实现要求

- 几何计算抽成 `internal fun` 纯函数，可直接单测（不需要真机）：
  - `ringMidRadiusOf(outerRadius, thicknessPx): Float` → `outerRadius - thicknessPx / 2f`
  - `leadPointOf(center, cos, sin, outerRadius, thicknessPx, lead: Float): Offset` → 环中线外推 `lead`
  - `elbowXOf(centerX, direction, outerRadius, elbowGap): Float`
- 常量集中：`LEAD_LENGTH = 4.dp`、`ELBOW_GAP = 4.dp`、`CALLOUT_WIDTH = 96.dp`。

### 2.6 验收

| 编号 | 检查点 |
|---|---|
| A-1 | 引线根部落在色块内部，肉眼看不到线头戳出色块外 |
| A-2 | 引线前半段与扇区方向一致，之后才折向水平 |
| A-3 | 折线在饼图外只兜一小段（约 4dp），不再有明显的外扩弯 |
| A-4 | 色块上不再有起点圆点 |
| A-5 | 长账户名（如「招行信用卡」）在 96dp 列宽下能单行放下 |
| A-6 | 标签仍不重叠、不出画布 |

## 三、② 待报销确认

### 3.1 现状

`ReimburseDialog` 只有「实际到账金额」一个输入；`ReimburseTxnUseCase.confirm(txnId, actualCents, now)` 生成收入流水时，`accountId` 固定为**原支出的付款账户**，`dateTime` 固定为**当前时刻**。

问题：
- 报销款实际到账的卡往往不是垫付时刷的那张（公司打工资卡、垫付刷的是信用卡）；
- 报销常在月底批量到账，日期不是操作那一刻；
- 时间影响明细排序，缺少用户控制。

### 3.2 对话框结构（自上而下）

| 顺序 | 控件 | 默认值 | 交互 |
|---|---|---|---|
| 1 | 只读说明 `支出 ¥xxx` | — | 文本 |
| 2 | **到账账户** | 原支出的付款账户 | 点击展开账户列表（底部弹层），行内显示账户名 + 当前余额；右侧箭头 |
| 3 | **报销日期** | 今天 | 点击弹 `EditorDatePickerDialog`（复用记账页日历 + 今天/昨天/前天快捷） |
| 4 | **报销时间** | 当前时刻（HH:mm） | 点击弹时间选择器（24 小时制） |
| 5 | **实际到账金额（元）** | 支出全额 | 数字键盘，可改 |
| 6 | 差额提示 `自付 ¥xxx` | — | 金额合法时显示，非法时显示「报销金额不能超过支出金额」 |
| 7 | 按钮 | — | 取消 / 确认（金额非法时置灰） |

日期与时间合成一个 `timestamp`：**日期取所选日、时间取所选时刻**，秒归零。

### 3.3 到账账户的筛选口径（**裁定：现金 / 储蓄卡 / 投资**）

需求方原话「仅资金账户」，最终确认口径为「除信用和借贷之外都算」。

```
可选 = accounts.filter { !hidden && type in (CASH, SAVINGS, INVEST) }
```

| 类型 | 是否可选 | 理由 |
|---|---|---|
| CASH | ✅ | 现金能收报销款 |
| SAVINGS | ✅ | 主场景（工资卡、微信、支付宝） |
| INVEST | ✅ | 证券账户现金余额能进账 |
| CREDIT | ❌ | 信用卡收到报销款会变成「多还款」，记账语义上应是「还信用卡」而不是收入 |
| DEBT | ❌ | 借贷账户是「某人欠我」，收款会改写成对方欠款的减少，与报销无关 |

按 `sortOrder` 排序；显示的余额取 `Account.balance`（仓库已带实时余额的版本）。

### 3.4 默认账户不可用时的兜底（**方案 A：不预选 + 提示**）

原支出的付款账户可能已被删除（进回收站）或已隐藏，此时：

- 到账账户**不预选任何值**；
- 在控件下方显示一行小字：「原账户已不可用，请选择到账账户」；
- 「确认」按钮置灰，直到选出一个账户。

**为什么不自动改选第一个资金账户**：自动填一个用户没看过的账户，等于替用户做了一个涉及钱的默认决定，而且从界面上看不出「我原来那张卡怎么没了」。宁可多一步点击，也不能让钱进错账户。

### 3.5 Use Case 签名

```kotlin
suspend fun confirm(
    txnId: String,
    actualCents: Long,
    accountId: String? = null,      // null = 沿用原支出账户（兼容老调用与老测试）
    dateTime: Long = System.currentTimeMillis(),
    now: Long = System.currentTimeMillis(),   // 审计时间，用于 reimbursedAt / updatedAt
): AppResult<ReimburseResult>
```

**两个时间要分清**：

- `dateTime` 是**这笔报销收入发生在哪一天**（用户选的），写进 `txn.dateTime` 与 `txn.dateKey`，影响明细分组、报表归属月、预算；
- `now` 是**这次操作的时刻**（系统时间），写进 `txn.createdAt` 与原账的 `reimbursedAt` / `updatedAt`。

把两者混成一个参数，用户把报销日期改成上月，回收站排序和「最近操作」就会跟着错乱。

**校验**：

| 条件 | 结果 |
|---|---|
| 账户不存在 | `AppError.Custom("到账账户不存在")` |
| 账户类型是 CREDIT / DEBT | `AppError.Custom("报销只能到账到资金账户")` |
| 账户已隐藏 | `AppError.Custom("到账账户不可用")` |
| `actualCents` 不在 `1..支出金额` | 同现有逻辑 |
| `dateTime` 早于原支出 `dateTime` | **不拦截**（见 3.6） |

**原支出账目保持不变**：金额、日期、账户、分类一个字符都不动，只由 `setReimbursed` 写 `reimbursedAmount` / `reimbursedAt` / `pendingReimbursement=false`。撤销逻辑完全不动——它按 `reimbursementOf(original.id)` 找那笔收入并硬删，与收入落在哪个账户无关。

### 3.6 报销日期早于支出日期（**裁定：不拦截**）

现实里确实有「先记账、后补凭证」导致日期填反的情况，但更常见的是用户手滑。两种处理都不完美：

- 拦截：会挡住「9 月垫付、10 月到账」这种**完全正常**的场景（如果用户把支出日期也填成 10 月），而且「到账早于支出」在财务上并非绝对错误；
- 放行：可能产生「10 月 5 日支出、10 月 1 日到账」的倒序记录。

决定放行，理由：**账目日期的准确性是用户的责任，App 不应替用户否决。** 明细按日期排序，倒序记录一眼可见，用户能自己改。这也与记账页一致——记账页允许把日期改到任意一天，不校验。

### 3.7 验收

| 编号 | 检查点 |
|---|---|
| B-1 | 默认到账账户 = 原支出账户，余额显示正确 |
| B-2 | 账户列表里没有信用账户与借贷账户 |
| B-3 | 改到账账户后，生成收入流水的 `accountId` 是新账户 |
| B-4 | 改日期与时间后，收入流水落在所选日期的明细分组里 |
| B-5 | 原支出的金额、日期、账户、分类均未改变 |
| B-6 | 撤销报销后，那笔收入被硬删，原账回到待报销 |
| B-7 | 原账户被删/被隐藏时，不预选、提示、确认置灰 |
| B-8 | 金额超过支出金额时确认置灰 |

## 四、③ 记一笔「⇄」图标连点无效

### 4.1 根因

`PaymentSection` 把开关状态**先算好**再传给按钮：

```kotlin
onToggle = { viewModel.setSplitMode(!state.splitMode) }
```

这里的 `state` 是**本次重组捕获的快照**。连点两下时，第二次点击回调仍绑定在同一个快照上，`!state.splitMode` 算出的值与第一次完全相同 → `setSplitMode(true)` 再 `setSplitMode(true)` → 状态没变。

这不是「点击太快被丢弃」，而是**布尔值在渲染时就固化成了常量**。

> 需求方确认：真机复现过。

### 4.2 修法

ViewModel 新增：基于**最新** state 翻转，不看 UI 传来的值。

```kotlin
/** 切换单选 / 组合。基于最新状态翻转，连点两次必定回到原点。 */
fun toggleSplitMode() {
    _state.update { it.copy(splitMode = !it.splitMode, splits = if (it.splitMode) emptyMap() else it.splits, dirty = true) }
}
```

`MutableStateFlow.update` 在 CAS 循环里执行，读到的一定是最新值，连点无论多快都能正确翻转。

**关闭时清空分摊**：沿用现有 `setSplitMode(false)` 的语义——组合模式里的分摊金额不能留到单选模式里悄悄生效。

**保留 `setSplitMode(on)`**：其余调用点（编辑已有组合账目时预置、恢复草稿）依赖「设为指定值」的语义，不删。`toggleSplitMode` 是新增的并发安全入口。

### 4.3 验收

| 编号 | 检查点 |
|---|---|
| C-1 | 连点两次：开 → 关 |
| C-2 | 连点三次：开 → 关 → 开 |
| C-3 | 关掉后分摊金额被清空 |
| C-4 | 打开组合后再次打开，不会把上一次的分摊带回来 |
| C-5 | 编辑一笔已存在的组合支付账目，初始仍是组合模式 |

## 五、④ 流水删除入口

### 5.1 现状

`TxnItem` 外面套了 `SwipeToDismissBox`：往左滑露出红底删除图标，松手即删。

问题：
- 与长按抽屉并列存在两套删除入口，行为还不完全一致（左滑无提示，批量删除也无提示）；
- 列表本身还要支持「点击进详情」「长按弹菜单」「批量勾选」三种手势，左滑是第四种，误触概率不低；
- 左滑之后 `SwipeToDismissBox` 会保留 dismiss 状态，如果列表 key 复用不当会出现「刚滑走的条目又回来但还是划走态」的错位。

### 5.2 目标形态

**移除**：

- `SwipeToDismissBox` 包裹层（含 `rememberSwipeToDismissBoxState`、`SwipeToDismissBoxValue`）
- `DeleteBackground()` 整个函数（红色背景 + 图标）
- 与之配套的 `background(surface)` 补丁（原本是为了防红底透出）
- `testTag("txn_swipe_xxx")`

**新增**：长按抽屉最底层新增一行「删除」。

抽屉最终顺序（自上而下）：

```
编辑
批量操作
报销 / 取消待报销
拆分
分期
──────────── 分隔线
更多操作
图标与文字为红色的「删除」   ← 新增，最底
```

**位置理由**：红色破坏性操作放在最底、且与上方常用项隔开，误触概率最低；这也是 Android 上 `ModalBottomSheet` 放「删除」的惯例。

**交互**：

```
点击「删除」
  → viewModel.delete(txn.id)      // 现有方法：softDelete + emit "已移入回收站"
  → 关闭抽屉（onDismiss）
```

不弹二次确认，与现有左滑删除、批量删除口径一致；反悔靠回收站（`已移入回收站` 提示 + 回收站保留 30 天）。

**视觉**：图标 `Icons.Outlined.DeleteOutline`，图标 `tint` 与文字 `color` 均为 `MaterialTheme.colorScheme.error`。为支持这一项，`ActionRow` 增加可选参数 `danger: Boolean = false`（默认 false，不影响其余行）。

**批量删除操作栏**：`BatchActionBar` 完全不动（已带红色「删除」）。

### 5.3 验收

| 编号 | 检查点 |
|---|---|
| D-1 | 左滑不再有任何删除效果，也不会露出红底 |
| D-2 | 长按弹出的抽屉最底部是「删除」，图标与文字为红色 |
| D-3 | 点击后该笔从列表消失，抽屉关闭，底部提示「已移入回收站」 |
| D-4 | 回收站里能看到这笔，可恢复 |
| D-5 | 批量模式下勾选多笔再删除，行为与改动前一致 |
| D-6 | 点击进详情、长按弹菜单、批量勾选三个手势都不受影响 |

## 六、⑤ 待报销按日期分组

### 6.1 范围

| 列表 | 是否分组 |
|---|---|
| 待报销 | ✅ 按日期分组、可折叠 |
| 已报销 | ❌ 保持平铺（最多 50 条，按报销时间倒序） |

### 6.2 分组规则

- **分组键**：`dateKey`（`yyyyMMdd` 整数，`Txn` 上已有冗余字段）
- **组顺序**：日期倒序（最近的在最上）
- **组内顺序**：`dateTime` 倒序（同一时刻再按 `createdAt` 倒序，保证稳定）
- **组头文案**：`日期 · N 笔`
  - 日期用 `DateUtils.friendlyDate`：今天 / 昨天 / 前天 / M月d日
  - 例：`今天 · 2 笔`、`11月8日 · 5 笔`
- **组头右侧**：该组合计金额（`¥xxx`）+ 折叠箭头（展开朝上、折叠朝下）
- **组头整行可点**：点任意位置都切换折叠
- **默认全部折叠**（需求方确认）：首次进入只看到组头，点开才见条目
- **展开状态会话级**：存在 ViewModel 的 `MutableStateFlow<Set<Int>>` 里，`rememberSaveable` 不用；离开页面再回来恢复默认折叠，进程重启也恢复默认
- **顶部「N 笔」汇总**：不变，仍是全部待报销笔数（不是可见笔数）

### 6.3 数据来源与排序

`TxnRepository.pendingReimbursement()` 对应的 DAO 查询已经是 `ORDER BY dateTime DESC, createdAt DESC`，口径与 6.2 一致。

**但 ViewModel 仍显式排序一次**：理由是这个查询的排序在 SQL 里，一旦 DAO 被改动（比如为别的页面调排序），分组顺序会静默变化而测试抓不到。显式 `sortedWith(compareByDescending{ dateTime }.thenByDescending { createdAt })` 让「分组顺序」成为 ViewModel 的契约，不依赖数据库实现细节。

> 不改 DAO：这个查询同时被首页待报销胶囊使用，改排序会牵动首页（虽然只影响顺序，但没有必要冒这个险）。

### 6.4 空态与边界

| 情况 | 表现 |
|---|---|
| 没有待报销 | 维持现有 `EmptyState`（「没有待报销的账目」） |
| 组内最后一笔被报销 | 该组头消失（组里没有条目就不渲染组头） |
| 报销后组还在 | 剩余条目保持展开状态，不会因为列表刷新而全部收起 |
| 组头合计 | 该组**当前**所有条目金额之和，报销后自动减少 |

### 6.5 验收

| 编号 | 检查点 |
|---|---|
| E-1 | 待报销按日期倒序分组，组头显示「日期 · N 笔」 |
| E-2 | 组头右侧有合计金额与箭头 |
| E-3 | 默认全部折叠，点组头展开，再点收起 |
| E-4 | 组内条目按时间倒序 |
| E-5 | 折叠状态下不渲染组内条目（不是透明度隐藏） |
| E-6 | 离开页面再回来，恢复全部折叠 |
| E-7 | 顶部「N 笔」始终是全部待报销笔数 |
| E-8 | 已报销列表仍为平铺，不受分组影响 |

按用户要求：**每一阶段都要对应测试，测试通过才进入下一阶段。**

| 阶段 | 内容 | 门禁 |

**排序理由**：

- S4 与 S5 同属待报销，S4 先（对话框），S5 后（列表），避免在同一次改动里同时调数据流与 UI 结构。

## 九、明确不做

| 不做 | 理由 |
|---|---|
| 报销时同时修改原支出的日期/账户 | 会破坏「原支出 = 真实发生的那笔消费」的事实记录；②的语义是「钱到账了」，不是「消费变了」 |
| 报销日期早于支出时的拦截与提醒 | 见 3.6 |
| 到账账户自动改选第一个可用账户 | 见 3.4，涉及钱的默认值不能猜 |
| 左滑保留但改为「左滑弹菜单」 | 四种手势叠在一行上本身就不合理，需求是移除 |
| 删除单笔时弹二次确认 | 与左滑、批量删除口径不一；反悔靠回收站 |
| 待报销图标的展开状态持久化 | 默认折叠 + 会话级展开，进页面就是要看「有几天没报」的概览，持久化会让每次进来看到的都是上次的局部视图 |
| 已报销也按日期分组 | 已报销最多 50 条且是「查历史」场景，平铺更好扫 |
| 改 DAO 的 `ORDER BY` | 该查询被首页胶囊共用，见 6.3 |
| 新增 schema 字段 | 五条全部落在现有字段上，`Txn.accountId` / `dateTime` / `dateKey` 已够用 |
