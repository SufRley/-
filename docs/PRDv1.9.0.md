## 一、底栏改为纯汉字

### 1.1 现状

`MainScreen.kt` 的 `XxjzBottomBar` 用 `NavigationBarItem` 同时渲染图标与标签：

```kotlin
icon = { Icon(iconOf(tab), contentDescription = tab.label) },
label = { Text(tab.label) },
```

### 1.2 定稿

**只保留汉字，去掉图标。** 三个 Tab 的文字：`明细`、`报表`、`账户`。

| 项 | 定稿 |
|---|---|
| 图标 | 全部移除 |
| 文字 | 保留，字号加大到 `titleSmall`（原 `labelMedium` 偏小，纯文字需要更醒目） |
| 选中态 | 未选中 `onSurfaceVariant`，选中 `primary` + `FontWeight.SemiBold` |
| 高度 | 沿用 `NavigationBar` 默认高度，不额外压缩 |
| 可访问性 | `NavigationBarItem` 没有 icon 时，把 `tab.label` 放进 `Modifier.semantics { contentDescription = ... }` |

> 为什么保留 `NavigationBarItem` 而不自己画 Row：选中指示器、水波纹、无障碍角色都由 Material3 提供，自绘等于把这些重新实现一遍。`icon` 参数传空 `{}` 即可。

## 二、账户页头部与另两个 Tab 齐平

### 2.1 现状

三个主 Tab 的顶部结构不统一：

| 页面 | 顶部实现 | 实际高度 |
|---|---|---|
| 明细 | `Column` + 自定义 `MonthHeader`（`Row`，`vertical 4.dp`） | 紧凑，约 48dp |
| 报表 | `Column` + 自定义 `WindowHeader`（同款 `Row`） | 紧凑，约 48dp |
| 账户 | **独立 `Scaffold` + `TopAppBar`**，标题「账户」 | 约 64dp + 状态栏 inset |

`TopAppBar` 自带高度与 inset 处理，导致账户页顶部比另两个明显高一截，出现「空位」。

### 2.2 定稿

**去掉 `Scaffold` 与 `TopAppBar`**，账户页改为与明细/报表同款的自定义 `Row` 头部：

```
[☰]  账户                          [资产报表] [＋]
```

| 项 | 定稿 |
|---|---|
| 左侧 | 菜单按钮（`menu_entry`），仅根 Tab 显示 |
| 中间 | 标题「账户」，`titleMedium` + `SemiBold`，**与 `MonthHeader` 的标签同字号同层级** |
| 右侧 | 资产报表入口（`account_report`）、新建账户（`account_add`） |
| 时间 | **账户页不显示时间**，`Row` 中间只放标题，不占位、不留空 |
| 高度 | 与 `MonthHeader` / `WindowHeader` 一致（`vertical 4.dp` 内边距 + `IconButton` 48dp） |
| 返回箭头 | 保留「非根 Tab 时显示返回箭头」的分支（`isRootTab`），从别处进入账户页仍可返回 |
| Snackbar | 改为页面内部的 `SnackbarHost`（不再依赖 `Scaffold`），位置贴底 |

> 不显示时间不等于留空：`Row` 用 `Modifier.weight(1f)` 让标题自然占满中间，右侧按钮靠右，视觉上不会出现「中间一块空白」。

## 三、借贷账户改为净值合并

### 3.1 现状与问题

v1.9.0 批二的模型是「一人一账户 + **建立时锁定方向**」：

- 我借出 → 方向 `LEND`，只能记「借出 / 收款」；
- 我借入 → 方向 `BORROW`，只能记「借入 / 还款」。

后果：**同一个人不能只有一个账户**。我先借给 A 100，后来向 A 借 30，系统里必须有两个 A（第二个显示「A(2)」），查这个人的总账要自己心算。

### 3.2 定稿：一个人 = 一个账户，余额是净值

| 项 | 定稿 |
|---|---|
| 账户方向 | **取消方向锁定**，`debtDirection` 不再参与任何校验与按钮显隐 |
| 账户含义 | 一个借贷账户 = 一个人（或一个往来单位） |
| 余额含义 | **净值**。正数 = 对方欠我（待收），负数 = 我欠对方（待还） |
| 符号约定 | 沿用 PRD 2.1：待收为正、待还为负 |
| 四种操作 | 借出 / 收款 / 借入 / 还款，**任意账户都可执行任意一种** |
| 上限校验 | **不保留**。收款/还款不做「不能超过待收/待还」的限制 |
| 坏账核销 | 仍只对「净额为正（待收）」的账户开放 |

### 3.3 净值如何形成

余额仍由流水聚合，聚合公式**完全不变**（`AccountDao.observeBalances()` 的四段 + 借贷两段）：

```
借贷侧  + Σ CASE WHEN debtAction IN ('LEND_OUT','REPAY') THEN amount ELSE -amount
```

举例（同一账户 A）：

| 操作 | 金额 | 该笔对 A 余额的影响 | A 的余额 |
|---|---|---|---|
| 借出 | 100 | +100 | **+100**（A 欠我 100） |
| 收款 | 60 | −60 | **+40** |
| 借入 | 30 | −30 | **+10** |
| 还款 | 50 | +50 | **+60** |
| 收款 | 80 | −80 | **−20**（我欠 A 20，显示「待还」） |

> 关键点：**余额符号会自然翻转**，不需要任何额外逻辑。这正是净值模型的好处——它就是一本跟某个人的流水账。

### 3.4 净资产的影响

**不变。** 净资产仍按符号拆分计入：

- 余额 ≥ 0 → 计入资产「借出款」
- 余额 < 0 → 计入负债「借入款」

净值合并只是让「一个人」可以同时出现在资产和负债两侧的**计算前**，计算后仍按最终符号归一边。因此 PRD 2.2 的「四种操作净资产不变」依然成立。

### 3.5 界面变化

**详情页**（`AccountDetailScreen`）：

| 项 | 现状 | 定稿 |
|---|---|---|
| 标题 | 按方向显示「待收」或「待还」 | 按**余额符号**显示，正数「待收」、负数「待还」、零「已结清」 |
| 金额 | `abs(balance)` | 不变 |
| 颜色 | 正绿负红 | 不变 |
| 按钮 | 按方向只显示一个 | **四个按钮全显示**：借出、收款、借入、还款；坏账核销仅余额 > 0 时显示 |

**记账面板**（`EditorSheet`）：

| 项 | 定稿 |
|---|---|
| 方向开关 | **保留**（「我借出 / 我借入」），但只用于决定**本次操作记哪种动作**，不再过滤账户列表 |
| 对方账户列表 | 显示**全部借贷账户**，不按方向过滤 |
| 无账户时 | 提示 +「＋ 新建借贷账户」保持不变 |

> 方向开关保留的理由：借出和借入是两种完全不同的动作，用户记一笔账时必须说清楚是哪一种。它跟「账户方向」是两件事，之前被混为一谈了。

**新建借贷账户**：不再询问方向，只填人名（+ 可选备注、约定还款日）。

### 3.6 存量数据处理

已有借贷账户的 `debtDirection` 字段**保留不删**（数据库不动），但：

- 不再参与校验；
- 不再用于过滤；
- 仅在「迁移旧台账」时用于判断补哪种动作；
- 界面不再显示。

**已存在的同名重名账户不自动合并**。理由：合并需要判断「用户是否想让它们合并」，自动合并会在余额上做出用户无法预期的改动。改为提供一个手动入口：

> 借贷账户详情页右上角增加「合并到…」入口，选择一个同类型的借贷账户，把当前账户的全部流水改挂到目标账户，然后删除当前账户。合并前弹确认，显示两边余额与合并后的净值。

## 四、饼图中心按中间切换 数字 / 百分比

### 4.1 现状

`AssetReportScreen.BreakdownPie` 的圆心固定显示「标签 + 金额」，点选扇区后额外多一行百分比。点扇区是「选中高亮」，没有显示模式切换。

### 4.2 定稿

圆心内容由**一个显示模式**决定，点击圆心切换：

| 模式 | 圆心显示（未选中扇区） | 圆心显示（已选中扇区） |
|---|---|---|
| 金额 | `合计` + `¥12,345.00` | `储蓄卡` + `¥3,000.00` |
| 百分比 | `合计` + `100%` | `储蓄卡` + `24.3%` |

| 项 | 定稿 |
|---|---|
| 切换方式 | 点击圆心区域（不只是点扇区） |
| 默认模式 | **金额** |
| 模式可见性 | 圆心下方加一行极小的提示「点击切换」（`labelSmall`，`onSurfaceVariant`，40% 透明），首次进入显示，切换过一次后不再显示 |
| 状态保持 | 同一页面内资产/负债两块**共用一个模式**，切换其一另一块同步 |
| 图例 | 不变，仍同时显示「百分比 + 金额」 |

> 为什么共用模式：用户在同一屏里看两个饼图，一块显示金额一块显示百分比会让人反复确认「是不是坏了」。

## 五、资产/负债构成按单个账户罗列

### 5.1 现状

`BreakdownCalculator.assets()` / `liabilities()` 按**账户类型**聚合：

- 资产 4 段：`现金` / `储蓄卡` / `投资` / `借出款`
- 负债 3 段：`信用欠款` / `借入款` / `储蓄卡透支`

因此「Q 银行卡」和「W 银行卡」都被并进「储蓄卡」一段，图例里看不到两张卡各自多少。

### 5.2 定稿：按账户拆段

| 项 | 定稿 |
|---|---|
| 切段粒度 | **一个账户一段** |
| 段标签 | 账户名（用户在账户管理中起的名字） |
| 折叠阈值 | 超过 **8 段**时，取金额最大的 **7 段**单列，其余合并为一段 `其他` |
| 「其他」排序 | 固定排在最后 |
| 零金额账户 | 不进饼图（沿用现有 `nonZero` 过滤） |
| 隐藏账户 | 仍整体不计入 |
| 投资账户 | 按市值计；`includeInNetAssets = false` 的仍在「未计入」提示里，不进饼图 |
| 借贷账户 | 按余额符号归入资产或负债，**一个账户一段** |
| 透支 | 现金/储蓄卡余额为负时，该账户的**绝对值**进负债段，标签仍是账户名 |
| 信用多还 | 信用账户余额为正时进资产段，标签仍是账户名 |

**颜色分配**：调色板扩到 8 色（现有 3 色不够用），按段序循环取色；`其他` 固定用中性灰，避免和真实账户撞色。

### 5.3 影响

`AssetBreakdown.total` 与 `NetAssetsCalculator` 的总额**必须完全一致**——这是硬约束，不是近似。回归时用「各段之和 == 总资产」做断言。

## 六、指纹解锁修复

### 6.1 两个真实缺陷

**缺陷 A：指纹开关被藏在应用锁下面**

```kotlin
if (state.prefs.appLockEnabled) {
    item { SwitchSetting("指纹 / 面容解锁", ...) }
}
```

「应用锁」默认关闭，因此「指纹 / 面容解锁」这一行**根本不渲染**。用户看到的安全区块只有「应用锁」一行，判定为「没有指纹选项」。

**缺陷 B：指纹弹窗永远弹不出来**

```kotlin
class MainActivity : ComponentActivity() { ... }        // 不是 FragmentActivity

(context as? FragmentActivity)?.let { AndroidBiometricGate(it) }   // 恒为 null
```

`as?` 转换恒失败 → `biometric` 恒为 `null` → `val gate = biometric ?: return@LaunchedEffect` 直接返回。**即使开关全开，锁屏也不会弹指纹。**

### 6.2 定稿

| # | 修法 |
|---|---|
| A | 指纹开关**移出** `if (appLockEnabled)`，提升为安全区块的常驻项 |
| A 联动 | 未开应用锁时点指纹开关 → 先弹「设置应用锁密码」对话框，设完自动打开应用锁并启用指纹（解锁必须有 PIN 兜底，不能只有指纹） |
| A 置灰 | 设备确实没有已录入生物特征时仍置灰，副标题说明原因 |
| B | `MainActivity` 改继承 **`FragmentActivity`**（`ComponentActivity` 的子类，Compose 页面零影响），使 `BiometricPrompt` 可用 |
| B 兜底 | `as? FragmentActivity` 仍保留，拿不到时**记录日志**而不是静默返回，避免下次再出现「无提示失效」 |
| 判定改进 | `hasEnrolledBiometric` 增加一条：`BIOMETRIC_WEAK` 不通但 `BIOMETRIC_STRONG` 通时也算可用（部分机型只支持强生物识别） |

### 6.3 验收

- 设备已录指纹 → 设置页「安全」区块直接可见「指纹 / 面容解锁」开关，可点击
- 开启应用锁 + 指纹 → 切后台再回前台，自动弹出系统指纹
- 指纹取消/失败 → 落到 PIN 输入页，**不计入密码错误次数**
- 设备未录指纹 → 开关置灰，副标题「未检测到已录入的指纹或面容」

## 八、明确不做

| 项 | 原因 |
|---|---|
| 借贷账户自动合并同名 | 会自动改动用户余额，改为手动「合并到…」 |
| 删掉 `debtDirection` 字段 | 要改 schema 与迁移，而它已不参与逻辑，删了没有收益 |
| 饼图段数无限展开 | 超过 8 段必然碎成难读的细条，「其他」折叠是常见做法 |
| 指纹失败时直接放行 | 等于关掉锁 |

## 九、执行顺序

**UI 三条（1、2、4）→ 报表口径（5）→ 借贷净值（3）→ 指纹（6）**

先做三条纯 UI 是因为互不干扰、可独立验证；借贷净值改动面最大，放中间以便留出充分的回归时间；指纹最后做，需要真机验证。
