## 二、借贷领域模型（批二核心，推翻 v1.8.0 的 D5）

### 2.1 语义定稿

借贷账户只回答一个问题：**这笔钱是我借给别人，还是别人借给我。**

一个借贷账户 = 一个人（对方）。建账户时锁定方向，之后只显示对应的两个操作。

| 方向 | `debtDirection` | 余额含义 | 显示 |
|---|---|---|---|
| 我借出（对方欠我） | `LEND` | 正数 = 待收 | `+¥1,000`（绿） |
| 我借入（我欠对方） | `BORROW` | 负数 = 待还 | `−¥500`（红） |

**余额符号约定**：待收为正、待还为负。与「账户余额」的既有语义一致（资产正、负债负），不需要额外字段来表达方向。

### 2.2 四种操作 + 坏账核销

| 操作 | `debtAction` | 借贷账户 | 资金账户 | 净资产 | 收支统计 |
|---|---|---|---|---|---|
| 借出 | `LEND_OUT` | `+amount` | `−amount` | **不变** | 不出现 |
| 收款 | `COLLECT` | `−amount` | `+amount` | **不变** | 不出现 |
| 借入 | `BORROW_IN` | `−amount` | `+amount` | **不变** | 不出现 |
| 还款 | `REPAY` | `+amount` | `−amount` | **不变** | 不出现 |
| 坏账核销 | `WRITE_OFF` | `−amount` | 无 | **减少** | 不出现 |

**坏账是唯一天然改变净资产的操作**，因为钱确实收不回来了。它必须出现在「资产变化记录」里，事件名「坏账核销：某某」。

**净资产不变的数例**（需求方确认的验收口径）：

```
初始：现金 10000，净资产 10000
① 借出 1000 给小王 → 现金 9000，小王账户 +1000（待收），净资产 10000
② 收到小王还 1000 → 现金 10000，小王账户 0，          净资产 10000
③ 找小李借入 500   → 现金 10500，小李账户 −500（待还），净资产 10000
④ 还小李 500       → 现金 10000，小李账户 0，          净资产 10000
```

四种操作在净资产与收支统计两个口径上均为零变化。借贷账户只是记录「这笔钱现在在谁手里」。

### 2.3 余额计算

单条借贷流水同时落在两个账户上：`accountId` = 借贷账户，`toAccountId` = 资金账户（坏账时为空）。

```
借贷账户余额 = initial
             + Σ(LEND_OUT) − Σ(COLLECT) − Σ(BORROW_IN) + Σ(REPAY) − Σ(WRITE_OFF)

资金账户余额 = initial
             + Σ(COLLECT) + Σ(BORROW_IN) − Σ(LEND_OUT) − Σ(REPAY)
```

两者互为相反数，因此**任一操作都不改变净资产**。这是设计的必然结果，不是巧合。

实现位置：`AccountDao.observeBalances()` / `observeWithBalances()` 的聚合 SQL，在现有四段（收入/支出/转账转入/转出）之后追加两段，**不改动原有四段**。

### 2.4 与资产报表的衔接

| 报表项 | 计算 |
|---|---|
| 资产构成 → 借出款 | Σ 余额 > 0 的借贷账户余额 |
| 负债构成 → 借入款 | Σ 余额 < 0 的借贷账户余额的绝对值 |
| 净资产 | 现金 + 储蓄卡 + 投资市值 + 借出款 − 信用欠款 − 借入款 |

即借贷账户余额**正常参与净资产求和**（正加负减），不做特殊排除。这与「借出后净资产不变」的验收口径一致：只有计入，才能与现金减少相抵消。

### 2.5 界面入口

| 入口 | 位置 | 说明 |
|---|---|---|
| 借出 / 借入 | 明细页 ＋ → 类型 Tab 第 4 项「借贷」 | 进入后先选方向（我借出 / 我借入），再选对方账户、资金账户、金额、日期 |
| 收款 / 还款 | 借贷账户详情页 | 「我借出」账户显示「收款」，「我借入」账户显示「还款」 |
| 坏账核销 | 借贷账户详情页 → 更多 | 二次确认后核销，余额归零 |

**删除**：
- 独立「借贷台账」页面
- 账户页顶部的「借贷台账」入口卡（v1.8.0 的 D5 作废）
- `Debt` 表保留但清空弃用（不 DROP，留作回滚保险）

## 三、信用账户分期（批二）

### 3.1 分期范围

| 项 | 定稿 |
|---|---|
| 可分期账户 | **仅信用账户**（信用卡、花呗类）。储蓄卡、现金、借贷、投资账户不可分期 |
| 分期对象 | 单笔消费（`scope=TXN`）、整期账单（`scope=BILL`） |
| 期数 | **由用户输入，不预设选项**。校验范围 2 ~ 60，超范围提示「请输入 2~60 之间的期数」 |
| 手续费 | 手动填写总额（可为 0） |
| 手续费摊法 | 用户二选一：`AVERAGE` 均摊到每期 / `FIRST` 首期一次收齐 |
| 起算账期 | 默认当前账单周期，可改 |

### 3.2 数据模型（新建 `installment` 表）

```sql
CREATE TABLE installment (
  id             TEXT    PRIMARY KEY,
  scope          TEXT    NOT NULL,   -- TXN（单笔消费）| BILL（整期账单）
  txnId          TEXT,               -- scope=TXN 时指向那笔消费；BILL 时为 null
  accountId      TEXT    NOT NULL,   -- 信用账户
  principalCents INTEGER NOT NULL,   -- 分期本金
  feeCents       INTEGER NOT NULL,   -- 手续费总额
  feeMode        TEXT    NOT NULL,   -- AVERAGE | FIRST
  periods        INTEGER NOT NULL,   -- 期数（用户输入 2~60）
  startBillKey   INTEGER NOT NULL,   -- 起始账期，yyyyMM
  createdAt      INTEGER NOT NULL
)
```

**`txn` 表一行都不改**，`TxnType` 也不加新值。

> 为什么新建表而不是把分期字段塞进 `txn`：分期信息（本金、期数、手续费、已还几期）是一组独立数据；塞进 `txn` 会迫使 `type` 多出一个「这不是一笔账」的取值，从而污染约 12 处 `when (type)` 分支和全部统计 SQL。多一张表，换 `txn` 语义干净。

### 3.3 每期金额计算（不落库，实时算）

```
perPrincipal = principalCents / periods          // 整除
remainder    = principalCents %  periods         // 余数并入最后一期

feePer = when (feeMode) {
    AVERAGE -> feeCents / periods                // 余数并入最后一期
    FIRST   -> if (期次 == 1) feeCents else 0
}

第 i 期应还 = perPrincipal + (i == periods ? remainder : 0)
            + feePer       + (AVERAGE 且 i == periods ? feeRemainder : 0)
```

`paidPeriods`（已还几期）**不落库**，由该分期关联的还款流水实时统计，避免两处数据各算。

### 3.4 账单周期与本期应还

**账期区间**（按需求方的花呗口径：账单日 15 号 → 本期覆盖本月 15 日到下月 14 日）：

```
若 today.dayOfMonth >= billDay:
    start = 本月 billDay 00:00
    end   = 下月 (billDay - 1) 23:59:59
否则:
    start = 上月 billDay 00:00
    end   = 本月 (billDay - 1) 23:59:59
```

**还款日** = `end` 次日之后第一个到达的 `repayDay`（同月或下月，按 `repayDay` 与 `billDay` 的相对位置推算）。

**两个数字都要显示**，避免歧义：

| 展示项 | 计算 |
|---|---|
| 本期消费总额 | 账期区间内所有 `EXPENSE` 流水金额之和（含已分期的全额），回答「这个月花了多少」 |
| **本期应还** | 账期区间内**未分期**消费 + 所有分期计划在本账期应还的期数金额，回答「这次要还多少」 |

已分期的消费由分期计划接管，不再按原样计入「本期应还」，否则会重复计算。

### 3.5 界面

信用账户详情页顶部新增账单卡：

```
┌─────────────────────────────────┐
│ 花呗              额度 ¥20,000   │
│ 本期应还  ¥3,240.00             │
│ 本期消费 ¥3,000.00 · 11/20 还款 │
│ 已用 ¥3,240 / 可用 ¥16,760      │
│ [ 分期 ]            [ 还款 ]    │
├─────────────────────────────────┤
│ 流水列表（原有）                 │
└─────────────────────────────────┘
```

- **分期** → 底部弹窗选「本期账单分期」或「选一笔消费分期」→ 输入期数（输入框）→ 填手续费 → 选摊法 → 确认
- **还款** → 输入金额，选资金账户，生成一笔还款流水，冲抵本期应还
- 流水列表里已分期的消费显示「已分 N 期」标签，点击可查看各期进度

### 4.1 第 5 条的键盘布局

```
┌───────────────────────────────┐
│  1     2     3   │  +        │
│  4     5     6   │  −        │
│  7     8     9   │  ×        │
│  .     0     ⌫   │  ÷        │
├───────────────────────────────┤
│           保 存               │
└───────────────────────────────┘
```

「=」不再是必经步骤。想看结果时可以按运算符联动求值（保留原行为），但保存不等它。

### 4.2 第 6 条的取舍说明

需求方选择「完全不弹」。已知代价：误触关闭会丢失已填内容。缓解措施：保存按钮常驻（第 5 条）降低了「想保存却关掉」的概率；输入框内容在关闭后不保留，不做草稿。

### 4.3 第 7 条的解锁流程

```
应用启动 / 从后台返回
  ├─ 未开启应用锁 → 直接进入
  └─ 已开启应用锁
       ├─ 已开启指纹开关 且 设备支持 且 已录入 → 自动拉起生物识别
       │    ├─ 成功 → 进入
       │    └─ 失败 / 取消 → 显示 PIN 输入页，可再点「改用指纹」
       └─ 否则 → 显示 PIN 输入页
```

「已开启应用锁」的定义：已设置 PIN。指纹开关依赖 PIN 存在，关闭 PIN 时联动关闭指纹。

## 五、数据库变更汇总

| 迁移 | 内容 | 回滚保险 |
|---|---|---|
| **v5 → v6** | `account` 加 `debtDirection` / `note` / `dueAt`；`txn` 加 `debtAction`；`debt` 表数据搬成账户后清空 | `debt` 表不 DROP |
| **v6 → v7** | 新建 `installment` 表 | 表可 DROP |

### 5.1 旧台账数据迁移规则

| 旧字段 | 迁移去向 |
|---|---|
| `counterparty` | → 账户名（同名合并？**否**，一人一条，重名加序号） |
| `direction` | → `debtDirection`（`LEND`→`LEND`，`BORROW`→`BORROW`） |
| `principal` | → 账户初始余额（`LEND` 为 `+principal`，`BORROW` 为 `−principal`） |
| `dueAt` | → `account.dueAt` |
| `note` | → `account.note` |
| 已还部分 | → 已有 `type=DEBT` 的还款流水补上 `debtAction`（`LEND` 补 `COLLECT`，`BORROW` 补 `REPAY`） |
| `writtenOff` | → 生成一条 `WRITE_OFF` 流水把余额核销归零 |

### 5.2 三个必须防的点

1. **迁移幂等**：`app_meta` 存标记位 `migration_v6_debt_done`，重跑不重复建账户。
2. **坏账不虚增资产**：`WRITE_OFF` 只核销，不进收支统计。
3. **余额聚合是核心**：SQL 改错会让所有账户余额一起错。必须有「迁移前后资金账户余额总额相等」的断言用例。

### 5.3 迁移带来的口径变化（需在升级提示中告知）

旧版本借贷**完全不参与净资产**。迁移后借出款计入资产、借入款计入负债，因此：

- 有未收借款的用户，升级后净资产会**上升**（等于待收总额）；
- 有未还欠款的用户，升级后净资产会**下降**（等于待还总额）。

这是口径修正，不是数据错误。旧版还保留着 `toAccountId` 的历史还款流水会同步影响资金账户；若旧流水缺少 `toAccountId`，则只补 `debtAction`、不动资金侧（旧版本现金本就没动），保持自洽。
